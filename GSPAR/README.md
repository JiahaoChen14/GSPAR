# GSPAR Usage and Implementation Guide

This directory contains the core GSPAR implementation: extracting spatial information for planning from 3D Gaussian Splatting (3DGS) scene models, building occupancy maps, planning 3D paths, interactive visualization, and experimental evaluation.

For a project overview, environment setup, and a quick single-scene workflow, see the repository-level [`README.md`](../README.md). This document focuses on the complete workflow, scene configuration, module organization, and planner extension points.

> Run all commands in this document from the repository root. Complete the environment setup described in the repository README and activate the appropriate Python environment first.

## 1. Method Overview

GSPAR provides two ways to use 3DGS scene information for path planning:

| Method | Representation Used for Planning | Current Global Planner | Current Local Optimization |
| --- | --- | --- | --- |
| GSPAR-Direct | Collision queries against the Gaussian scene | RRT | Continuous path optimization |
| GSPAR-Global | Occupancy map built from the Gaussian scene | JPS | EGO |

GSPAR-Direct constructs collision queries from Gaussian positions, shapes, rotations, and opacity. It searches and optimizes paths in continuous space without first building a global occupancy map.

GSPAR-Global first processes and voxelizes the Gaussian scene to build a reusable occupancy map. Once built, path planning uses that map and does not need to access the original Gaussian parameters for every query.

The planners in this repository are the implementations used in the paper's experiments. Other global search and trajectory optimization methods can be integrated as needed; see [Extending the Planners](#7-extending-the-planners).

## 2. Recommended Workflow

For scenes whose data has already been preprocessed or whose trained 3DGS model is available, configure them centrally in [`configs/dataset.txt`](../configs/dataset.txt), then generate the processing commands for each scene.

1. Prepare the scene data, a compatible 3DGS checkpoint, and its training configuration.
2. Add scene names, input paths, output paths, and map parameters to `configs/dataset.txt`.
3. Run `GSPAR/scripts/generate_voxel_scene_command_txts.py` to generate command files for each scene.
4. Open the relevant command file and run the required scene-preparation and map-building commands.
5. Use the GUI for interactive path planning, or run batch experiments through the batch modules.

GSPAR-Direct can plan directly against a loaded Gaussian scene. GSPAR-Global requires an occupancy map before it can be used by the planning pipeline.

### 2.1 Preparing Scene Data

The recommended data layout is:

```text
dataset/
└── <dataset>/
    └── <scene>/
        ├── images/
        └── sparse/
            └── 0/

output/
└── <dataset>/
    └── <scene>/
        ├── training_config.yaml
        └── checkpoints/
            └── final.pt
```

| File or Directory | Purpose |
| --- | --- |
| `images/` | Scene images; exact requirements depend on the dataset loader and workflow |
| `sparse/0/` | COLMAP cameras and sparse reconstruction data |
| `final.pt` | Trained 3DGS checkpoint |
| `training_config.yaml` | Matching training configuration used to load and visualize the scene |

This layout is recommended but not required. Data may be stored elsewhere as long as `configs/dataset.txt` contains the correct paths and the data paths in the training configuration remain valid.

Scene loading is integrated with NeRFICG. If a 3DGS model was generated by another tool, verify that its format is compatible with the current loader. Format conversion or a loader extension may be required; changing only the file extension does not convert a model.

### 2.2 Configuring Scenes

Edit this file at the repository root:

```text
configs/dataset.txt
```

It describes scene inputs, 3DGS models, map outputs, and optional experimental reference data. The next section provides an example and field descriptions.

### 2.3 Generating Scene Commands

Run from the repository root:

```bash
python GSPAR/scripts/generate_voxel_scene_command_txts.py
```

By default, command files are generated under:

```text
GSPAR/voxel_command_txts/<dataset>/<scene>.txt
```

For example:

```text
GSPAR/voxel_command_txts/
└── scannetpp/
    ├── Classroom.txt
    ├── Kitchen.txt
    └── Office.txt
```

The script only generates command text. Open the `.txt` file for the desired scene, verify its input paths and parameters, and then run the required commands from it.

### 2.4 Running the Required Steps

Depending on the configured data, a command file may contain:

| Step | Purpose | When It Applies |
| --- | --- | --- |
| GT axis alignment | Prepare the scene coordinate transform | When corresponding GT data is configured |
| Gaussian scene voxelization | Build a GSPAR-Global occupancy map | When using GSPAR-Global |
| nvblox TSDF and ESDF construction | Build depth-based reference maps | For the corresponding comparison experiments |
| nvblox TSDF-to-voxel conversion | Prepare data for map comparison | For the corresponding mapping evaluation |
| GT mesh voxelization | Prepare an independent geometric reference | When GT is available and required for evaluation |
| Voxel-grid alignment check | Verify coordinate and grid relationships between maps | When comparing multiple maps |
| GUI launch | Load the scene and maps and perform planning | For interactive use |

Select only the steps required for your goal. Standard GSPAR-Direct and GSPAR-Global planning does not require GT data, nvblox reference maps, or SplatNav.

If the configuration includes coordinate alignment, all subsequent map construction, endpoint selection, and evaluation must use the corresponding transform. Different representations must share the same coordinate system.

## 3. Scene Configuration

### 3.1 Complete ScanNet++ Example

The following configuration shows a complete organization of ScanNet++ scene inputs and experimental reference data:

```text
scannetpp:
    format:
        scenes: Classroom, Kitchen, Office, Storage, Bedroom, ConferenceRoom, CopyRoom, Plant, Apartment, Bathroom
        images: dataset/scannetpp/{scene}/images_2
        sparse: dataset/scannetpp/{scene}/sparse/0
        3dgs model: output/scannetpp/{scene}/checkpoints/final.pt
        training_config: output/scannetpp/{scene}/training_config.yaml
        output: GSPAR/outputs/scannetpp/{scene}
        gt: dataset/scannetpp/{scene}/gt
        voxel size: 0.05
        scene type: indoor
        nvblox version:
            sparse: dataset/scannetpp/{scene}/sparse/0
            depth: dataset/depth/scannetpp/{scene}/depth_maps
```

`{scene}` is replaced with each name listed in `scenes`, producing the corresponding input paths, output paths, and commands.

For example, the model path for `Classroom` is:

```text
output/scannetpp/Classroom/checkpoints/final.pt
```

Its map output directory is:

```text
GSPAR/outputs/scannetpp/Classroom
```

### 3.2 Field Descriptions

| Field | Meaning |
| --- | --- |
| `scannetpp` | Dataset identifier used to organize scenes and generated results |
| `format` | Path templates and parameters shared by multiple scenes |
| `scenes` | Comma-separated list of scene names |
| `images` | Path to raw or preprocessed scene images |
| `sparse` | Path to the scene's COLMAP sparse data |
| `3dgs model` | Path to the trained 3DGS checkpoint |
| `training_config` | Path to the training configuration associated with the model |
| `output` | Output directory for the current scene's maps and generated artifacts |
| `gt` | Optional GT geometry used by the relevant alignment and evaluation workflows |
| `voxel size` | Voxel size in the current scene's coordinate units |
| `scene type` | Scene type, such as `indoor` or `outdoor` |
| `nvblox version.sparse` | Camera and pose data used by the nvblox workflow |
| `nvblox version.depth` | Depth data used by the nvblox workflow |

`gt` and `nvblox version` support the corresponding scene-alignment, evaluation, and comparison workflows. Standard GSPAR path planning does not depend on this reference data.

Requirements for `images` and `sparse` depend on the scene-loading, GUI, and preprocessing workflows. Even if a checkpoint is already available, verify that its `training_config.yaml` can load the scene correctly.

### 3.3 Example Without Evaluation Reference Data

To use custom scenes only for GSPAR path planning:

```text
my_dataset:
    format:
        scenes: scene1, scene2
        images: dataset/my_dataset/{scene}/images
        sparse: dataset/my_dataset/{scene}/sparse/0
        3dgs model: output/my_dataset/{scene}/checkpoints/final.pt
        training_config: output/my_dataset/{scene}/training_config.yaml
        output: GSPAR/outputs/my_dataset/{scene}
        voxel size: 0.05
        scene type: outdoor
```

Replace the dataset name, scene names, paths, voxel size, and scene type with your own settings, then run the command-generation script.

## 4. GSPAR-Direct

The main implementation is under [`path/gspar_direct/`](path/gspar_direct/).

GSPAR-Direct takes a reconstructed Gaussian scene, a start point, a goal point, and a robot radius. For each query, the system selects relevant Gaussians and constructs collision queries from their positions, principal-axis scales, rotations, and opacity.

The current implementation first checks the direct connection between the start and goal. If an obstacle must be avoided, it uses RRT to find a coarse path and then applies continuous path optimization.

| File | Function |
| --- | --- |
| `gaussian_field.py` | Manages Gaussian scene information used by the current planning query |
| `gaussian_collision.py` | Gaussian collision constraints and collision costs |
| `rrt.py` | RRT search in continuous 3D space |
| `rrt_collision.py` | Collision checking for RRT path segments |
| `trajectory_optimizer.py` | Continuous path optimization |
| `planner.py` | Main GSPAR-Direct planning interface |

GSPAR-Direct does not require a prebuilt GSPAR-Global occupancy map. The Viewer described below can load a scene and define planning queries.

## 5. GSPAR-Global

GSPAR-Global consists of map construction followed by path planning on the map. Occupancy maps can be saved and reused for multiple subsequent queries.

### 5.1 Building an Occupancy Map from a Gaussian Scene

The core implementation is under [`mapping/gaussian_occupancy/`](mapping/gaussian_occupancy/), with `build_sparse_voxel_map.py` as its main entry point.

Using commands produced by the scene command generator is recommended because this keeps input paths, output paths, and scene parameters consistent. A standalone example is:

```bash
python GSPAR/mapping/gaussian_occupancy/build_sparse_voxel_map.py \
  --checkpoint output/<dataset>/<scene>/checkpoints/final.pt \
  --output-prefix GSPAR/outputs/<dataset>/<scene>/voxel_map \
  --voxel-size 0.05 \
  --block-size 8 \
  --scene-padding 0.02 \
  --scene-type outdoor
```

Replace `<dataset>` and `<scene>` and adjust the parameters for the scene. These names are placeholders and must not remain literally in the shell command.

Map construction consists mainly of:

1. Geometry filtering based on opacity, local spatial support, position relative to scene bounds, Gaussian size, and related information.
2. Computing the effective spatial support of retained Gaussians.
3. Evaluating Gaussian spatial contributions at voxel locations.
4. Accumulating occupancy evidence and determining voxel occupancy states.
5. Saving the sparse occupancy map and associated metadata.

Geometry filtering suppresses Gaussians that may create false obstacles, such as isolated floaters, abnormal boundary Gaussians, or oversized Gaussians. It considers multiple geometric factors rather than filtering by opacity alone.

Typical outputs are:

```text
voxel_map.npz
voxel_map.json
```

The `.npz` file stores map data, while `.json` stores voxel size, spatial bounds, and related metadata. Keep both files together when using or moving a map.

### 5.2 Global Path Search

Global planning is implemented under [`path/global_path/`](path/global_path/):

| File | Purpose |
| --- | --- |
| `astar_world_path.py` | A* search on an occupancy map |
| `jps3d_world_path.py` | JPS search on an occupancy map |
| `esdf_astar_world_path.py` | ESDF-related search pipeline |

GSPAR-Global currently uses JPS for global path search. JPS is an accelerated variant of A*, and its native implementation is under [`path/jps3d/`](path/jps3d/).

### 5.3 Local Path Optimization

Local optimization is implemented under [`path/local_path/`](path/local_path/). GSPAR-Global uses `ego_occupancy_path.py` to further optimize the coarse global path.

This directory also contains `stomp_esdf_path.py`, used for the corresponding nvblox ESDF comparison experiments.

## 6. Interactive Viewer

Interactive visualization is implemented under [`gui/`](gui/), with `launchViewerOverlay.py` as the main entry point.

To load only a Gaussian scene:

```bash
python GSPAR/gui/launchViewerOverlay.py \
  --training-config-path output/<dataset>/<scene>/training_config.yaml \
  --checkpoint-path output/<dataset>/<scene>/checkpoints/final.pt
```

To also load a GSPAR-Global occupancy map:

```bash
python GSPAR/gui/launchViewerOverlay.py \
  --training-config-path output/<dataset>/<scene>/training_config.yaml \
  --checkpoint-path output/<dataset>/<scene>/checkpoints/final.pt \
  --voxel-map GSPAR/outputs/<dataset>/<scene>/voxel_map
```

The Viewer can define a start point, goal point, and robot radius, and visualize the Gaussian scene, occupancy map, and planned path. When loading reference maps, verify that they use the same coordinate system as the Gaussian scene.

For scenes managed through `dataset.txt`, prefer the GUI launch command generated in the scene's command file.

## 7. Extending the Planners

The planning algorithms in this repository are the reference implementations used in the paper's experiments; they are not the only possible planners for GSPAR. GSPAR focuses on obtaining spatial information for planning from 3DGS scenes, while downstream planners can be replaced to suit an application.

### 7.1 Extending GSPAR-Direct

The current implementation uses RRT for global search followed by continuous path optimization. Its core capability is collision querying against the Gaussian scene.

Other algorithms that use state or path-segment collision checks can also be integrated. A new planner must connect its queries to the existing Gaussian collision model and use consistent robot radii, coordinate systems, and path outputs.

Relevant code is under:

```text
GSPAR/path/gspar_direct/
```

### 7.2 Extending GSPAR-Global

The current implementation uses JPS for global search and EGO for local optimization. Once a Gaussian scene has been converted into an occupancy map, other search algorithms or trajectory optimizers designed for 3D occupancy representations can also be integrated.

For example, the existing A* implementation can serve as a reference for extending global search, or a custom optimizer can process the coarse path.

Relevant code is under:

```text
GSPAR/path/global_path/
GSPAR/path/local_path/
GSPAR/path/planning.py
```

These directories contain the primary extension points. Integrating a new method may also require changes to planning dispatch, parameter passing, the GUI, or evaluation interfaces.

### 7.3 Conventions That Must Remain Consistent

| Convention | Requirement |
| --- | --- |
| Coordinate system | The start, goal, map, and output path must use the same coordinates |
| Scene scale | Voxel size, robot radius, and path length must use consistent units |
| Collision semantics | Define obstacle classification, robot dimensions, and handling of unobserved regions |
| Path validation | Perform appropriate collision checks on path segments or continuous trajectories |
| Result interface | Return compatible path and status information to the GUI and evaluation pipeline |

## 9. Experimental Evaluation and Batch Execution

Evaluation code is under [`evaluation/`](evaluation/), and batch experiment entry points are under [`batch/`](batch/).

The main batch entry points are:

```bash
python -m GSPAR.batch.mapping
python -m GSPAR.batch.paths
python -m GSPAR.batch.ablation
```

These commands show the module entry points. Before running them, configure the datasets, scenes, reference data, and experiment parameters for the task.

### 9.1 Mapping Evaluation

Depending on the available data, mapping can be evaluated against independent GT geometry or by comparing the GSPAR-Global map with an nvblox reference map.

Independent GT evaluation measures differences between the map and reference geometry. Comparison with an nvblox map measures consistency between two representations. When independent GT is unavailable, an nvblox reference map should not be treated as the true scene geometry.

### 9.2 Path-Planning Evaluation

The main implementation is under `evaluation/path_planning/`:

| File | Function |
| --- | --- |
| `generate_endpoints.py` | Generates planning start and goal points |
| `batch_compare.py` | Runs planning comparisons across methods |
| `metrics.py` | Computes path-planning metrics |

Comparison experiments must use the same endpoints, robot radius, coordinate system, and evaluation rules. A method's own planning-success result may differ from validation of that path against an independent reference map.

### 9.3 Building an nvblox Map from 3DGS-Rendered Depth

The relevant entry point is:

```text
GSPAR/mapping/build_rendered_depth_nvblox_map.py
```

This pipeline builds an nvblox reference map from depth rendered by 3DGS and is intended for comparison experiments with a controlled input source. It is not required for standard GSPAR path planning.

The rendered depth, camera poses, and output map must use consistent coordinate conventions. Query the script's `--help` output for command parameters and use them with the batch experiment workflow.

## 10. Native Components

### 10.1 JPS3D

The JPS backend currently used by GSPAR-Global is under `path/jps3d/`. Install its build dependencies, then run from the repository root:

```bash
cmake --fresh \
  -S GSPAR/path/jps3d \
  -B GSPAR/path/jps3d/build \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_PREFIX_PATH="$CONDA_PREFIX"

cmake --build GSPAR/path/jps3d/build --parallel
```

### 10.2 nvblox GPU SDF

The nvblox TSDF and ESDF construction component is under `nvblox_gpu_sdf/`. It is primarily used to build depth-based reference maps for comparison experiments.

After installing CUDA, nvblox, and the required build dependencies, run:

```bash
cmake --fresh \
  -S GSPAR/nvblox_gpu_sdf \
  -B GSPAR/nvblox_gpu_sdf/build \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_PREFIX_PATH="$CONDA_PREFIX"

cmake --build GSPAR/nvblox_gpu_sdf/build --parallel
```

Standard GSPAR-Direct and GSPAR-Global planning does not require an nvblox reference map to be built.

## 11. Coordinate Systems and Scene Scale

The following spatial quantities must share a consistent coordinate system and scale:

- Gaussian positions and shape parameters.
- Start and goal points.
- Voxel size.
- Robot radius.
- Occupancy maps and planned paths.
- Reference maps or GT geometry used for evaluation.

`voxel size` and `--voxel-size` use the coordinate units of the current 3DGS scene. For example, `0.05` represents 5 cm only when the scene itself uses metric scale.

Different datasets and reconstructions may use different scales. Do not assume that one scene unit equals one meter. Verify the scene scale before setting the robot radius and voxel size.

If scene alignment or scale transformation has been applied, all subsequent map construction, GUI queries, and evaluation must use the transformed spatial convention.

## 12. Generated Data

The recommended default output location for maps and experimental results is:

```text
GSPAR/outputs/<dataset>/<scene>/
```

Typical artifacts include occupancy maps, map metadata, paths, planning-evaluation records, mapping-evaluation results, and ablation results. The corresponding batch workflow manages the exact experiment directory structure.

Scene command text is written by default to:

```text
GSPAR/voxel_command_txts/<dataset>/<scene>.txt
```

Regenerate command files after modifying `dataset.txt`. If map parameters or input models change, rebuild the affected maps; regenerating command text alone does not update existing maps.
